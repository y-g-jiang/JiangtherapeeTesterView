# JPTC Collect — 贡献者采集与分析工具

设计文档 · 2026-08-11 · 阶段 0–2

## 1. 这是什么

一个发到别人手上的桌面应用。对方按流程拍完，把 RAW 拖进来，工具解码、统计、产出**可回收的数据文件**寄回。分析和结论仍然在 [ptc-compare](../../../../ptc-compare/) 那边做。

对方是摄影师，不是工程师。所以工具的第一职责不是算得快，是**让不合格的数据在对方那里就被拦下**，而不是在我这里被发现。

### 非目标

- 不做任何结论展示（那是 ptc-compare 的事）
- 不修图、不渲染、不导出可视图像
- 不联网、不上传（产出文件由对方自行寄回）

## 2. 三个入口与它们的依赖

```
入口 3  黑场对（每 ISO 两张，全 ISO 段）
          ├─ BL(ISO)        每个 ISO 的黑电平
          ├─ RN_DN(ISO)     每个 ISO 的时域读噪
          └─ 噪声谱          差分后逐通道 FFT
                │
入口 2  ISO gain 阶梯（固定场景，扫 ISO）
          └─ 需要 BL(ISO) ──┘
          └─ 相对 gain 曲线 g(ISO)/g(ref)
                │
入口 1  PTC 平场对（单 ISO，多快门）
          └─ 需要 BL ───────┘
          └─ 绝对 g(ref)、PRNU、FWC
                │
          三者合成：全 ISO 段绝对 gain、以电子计的读噪、动态范围
```

**拍摄顺序与构建顺序都是 3 → 2 → 1。**黑电平是另外两个入口的输入，先有它，后面两步才有意义。

## 3. 运行形态

Electron + React + TypeScript，**全本地，运行时不联网**。

### 3.1 RAW 解码：原生 LibRaw，从 GitHub 源码固定版本编译

一开始我打算复用主项目的 WASM，理由是「采集端与分析端要用同一个解码器」。这个理由不成立，作废：**分析端 ptc-compare 只读 CSV，从不碰 RAW。**会解码的是 Jiangtherapee Online 主项目，而它不在这条流水线上。

真正的决定性事实是另一个：**打包好的 LibRaw-Wasm 给不出 Bayer mosaic。**它的 JS 接口只有 `open` / `metadata` / `imageData`，而 `imageData` 走完整 `dcraw_process()` 出 RGB。要拿 `imgdata.rawdata.raw_image` 必须重新编译并加绑定——既然横竖要从源码编，编成原生不比编成 WASM 难，还快，还省掉整套 emscripten 工具链。

（顺带记录：主项目 `vendor/libraw-wasm/` 下的 `libraw.wasm` 与 `libraw.min.js` 都是 0 字节的占位空文件，实际用的是 `LibRaw-Wasm-main/dist/`。）

做法：LibRaw 源码作为 git submodule 固定到具体 tag，node-gyp 编译成 Node 原生插件，各平台预构建。版本号写进每个产出文件的头 `#Decoder:`，并用黄金文件（一组已知 RAW → 已知统计量）钉住——这比共享解码器更强，因为依赖被写明了、可核对。

### 3.2 只 unpack，绝不 process

需要的只有 **raw mosaic + EXIF**。调 `open_buffer()` + `unpack()` 拿 `rawdata.raw_image`，**永不调用 `dcraw_process()`**。去马赛克、白平衡、色彩变换全都不做——它们既是性能的大头，又会破坏我们要测的统计量。

### 3.3 速度预算

诚实地说，解码器不是速度的决定因素，这两件事才是：

| 决定 | 影响 |
|---|---|
| 只 unpack 不 process | 数倍，且避免统计量被污染 |
| 按文件并行（worker_threads） | 接近核数倍 |
| 流式处理，不把整批解码结果留在内存 | 决定能不能跑完 |

以 40 张 28.6 MB NEF 为例：I/O 合计 1.14 GB，原生 unpack 单张约 0.1–0.2 s，多线程后**整批是 I/O 受限的**。原生相对 WASM 的 2–4 倍优势只作用在解码这一段。

真正的计算大头是入口 3 的整幅 FFT：24 MP 拆四通道各 6 MP，Welch 分段后每 ISO 每通道约 90 个 512² 段，20 个 ISO 合计约七千次 512² FFT——几秒量级，可接受。

默认并行度取**逻辑核数的一半**，可在设置里调。这是别人的机器，不该跑满。

## 4. 阶段 0：共享地基

三个入口全部压在这上面，先定死。

### 4.1 拍摄模式录入

**点击任何输入之前必须填完。**未填完的按钮禁用，不是提交后报错。

| 字段 | 取值 | 为什么必须 |
|---|---|---|
| 机身 | 自由文本 + 从 EXIF 预填 | |
| 固件版本 | 自由文本 + 从 EXIF 预填 | 同机身不同固件的读出可以完全不同 |
| 快门类型 | `mech` / `efcs` / `elec` | 入口 2 的快门标称值准不准全靠它 |
| 压缩 | `lossless` / `uncompressed` / `lossy` | 有损压缩会改噪声统计，必须能筛掉 |
| 位深 | 12 / 14 / 16 | |
| **量化步长** | 由位深与容器推出，可手动覆盖 | 见 §4.3，全表最关键的一个数 |
| 镜头 | `none-bodycap` / 型号 | 黑场必须机身盖；有镜头的黑场不可信 |
| 长曝光降噪 | 必须勾「已关闭」 | 勾不上就不让继续 |
| 高感降噪 | 记录设置值 | 部分机器会动 RAW |
| 环境温度 | 可选，摄氏 | 暗电流与温度强相关 |

### 4.2 文件命名

产出文件名编码模式，人眼可读、机器可解析：

```
<brand>-<model>_<fw>_iso<n|range>_<shutter>_<compression>_<bitdepth>bit_<entry>_<date>.<ext>

panasonic-s1m2_v1.2_iso100_mech_lossless_14bit_ptc_20260811.csv
panasonic-s1m2_v1.2_iso50-25600_elec_lossless_14bit_dark_20260811.csv
panasonic-s1m2_v1.2_iso50-25600_elec_lossless_14bit_isogain_20260811.csv
```

同样的字段也写进文件头，**文件名与文件头不一致时以文件头为准**，并在导入侧报警——文件名会被人改，文件头不会。

### 4.3 量化步长的判定

分析端做 Sheppard 修正（`sigma^2_true = sigma^2_measured - q^2/12`）必须知道 `q`，而 `q` **从统计量里反推不出来**。工具在这里有优势：它能看到原始码值。

判定方法：取一张暗场的原始 mosaic，求相邻码值之差的非零最小公约数。12 bit 装进 16 bit 容器的文件，所有码值都是 16 的倍数，`q = 16`；14 bit 原生则 `q = 1`。

结果写进文件头 `#AdcStep:`。允许手动覆盖，但默认由实测决定，不由位深猜测。

### 4.4 合格性检查

在对方那里就拦住，每条都要给出人话理由与补拍建议：

| 检查 | 判据 |
|---|---|
| 帧数成对 | 每个设置恰好两张 |
| 设置一致 | 一对之内 ISO、快门、光圈、压缩必须相同 |
| 时间接近 | 一对之内拍摄时间差超过阈值就警告（温漂） |
| 无长曝光降噪 | EXIF 能读则读，读不到则依赖勾选 |
| 黑场确实是黑的 | 均值减黑电平后接近零，且无亮区（漏光） |
| 平场确实是平的 | 中心区域梯度小于阈值 |
| 未钳位 | 逐通道统计顶到上限的像素比例 |
| 位深与压缩符合声明 | 与 EXIF/解码结果对账 |

## 5. 阶段 1：入口 3 —— 黑场对

### 5.1 拍摄流程（呈现给对方）

机身盖，无镜头。最低 ISO 到最高 ISO，每档两张。快门任意但一对之内相同，建议用能达到的最短快门以压低暗电流。长曝光降噪关闭。

### 5.2 计算

对每个 ISO：

1. 解码两张的 mosaic，拆成 R / G1 / G2 / B 四个平面
2. `BL_ch = mean(A_ch)` 与 `mean(B_ch)`，两者都记
3. `D = A − B`，逐通道
4. 坏点剔除：对 `D` 做迭代 sigma clip，**k = 3.5**，收敛后把 std 除以 `sqrt(0.9969)` 补回被剪掉的真噪声

   固定偏移的热点在差分里精确抵消，所以 `D` 上剩下的大偏离只可能是时域异常像素或宇宙线；这使差分帧成为找它们的正确地方。剪切会连带削掉要测的噪声，截断高斯的方差有闭式解，`k=3.5` 处修正后偏差 ≤ 0.1%，且剔掉 96% 的宇宙线。`k < 3` 时迭代剪切会过收敛，闭式修正不再成立——**不要放宽到 3 以下**。
5. `RN_DN(ISO, ch) = std_clipped(D_ch) / sqrt(2) / sqrt(0.9969)`
6. 谱：见 §5.3

### 5.3 噪声谱：每个 ISO 十六条一维谱

**是一维谱，不是二维。**每通道沿行一条、沿列一条，单帧一套、差分一套：

    4 通道 × {横, 纵} × {单帧, 差分} = 16 条

`横` 是把每一行各自变换后对所有行取平均，`纵` 反之。行方向的平均本身就是方差抑制手段——2172 行平均下来谱已经很干净，不需要再沿行分段。

#### 必须逐通道，不能对 mosaic 整幅做

CFA 的两像素周期会在谱上砸出巨大假峰，把真实结构淹没。先按 CFA 相位拆成 R / G1 / G2 / B 四个平面，各自变换。

#### 整幅窗，chirp-z，不补零

窗长就是通道平面的整行/整列长度，不截断、不补零到 2 的幂。任意长度用 **chirp-z（Bluestein）**做精确 DFT。

主项目 [`utils/math.ts`](../../../../Jiangtherapeemaster/utils/math.ts) 的 `FFT` 类**已经实现了 Bluestein**，直接移植。要注意一个容易被误解的地方：Bluestein 内部仍会把**卷积**补到 2 的幂（长度 M ≥ 2N−1），但那是卷积的 padding，出来的是精确的 N 点 DFT——与「把信号补零后变换」是两回事。

现有的 `calculatePowerSpectrum` 走 Welch 分段（`segLen = 2N/(nSegments+1)`）。传 `nSegments = 1` 时 `segLen = N`，正好退化为整幅窗，代码不用改。

#### 窗函数与归一化

**默认 Hann。**减完均值 DC 就没了，但行方向的低频成分（暗场里的辉光、平场里的渐晕）不加窗会向全谱泄漏，而条纹本身是窄带的——正是最怕被泄漏盖住的东西。2000 多行平均之后，Hann 带来的分辨率损失无关紧要。

归一化用 `1/Σw²`，主项目的实现已经是对的。窗的选择写进文件头。

#### 频率单位

拆通道之后，一个通道平面像素跨两个传感器像素。谱按**每通道平面像素的周期数**记录（第 k 个 bin = k/N），Nyquist 在 0.5。换算到传感器像素要再除以 2，这一点写进文件头，不在数据里预先换算。

#### 差分谱不预先减半

差分使功率翻倍。文件头写 `#DiffPowerFactor: 2`，**数据保持原值**，减半由分析端做。理由与 §6.4 一致：原始记录留在原始层。

#### 白拿的第三套：固定图案谱

    单帧谱 − 差分谱/2 = 固定图案的谱

这回答的正是看噪声谱时最想问的那个问题——**这道条纹是固定的还是每帧随机的**。两个都是噪声估计，相减会放大噪声，但有两千行平均打底，够用。不额外存，分析端算。

#### A/B 一致性检查

单帧谱「随便挑一个」即可，但两张都算一遍几乎不要钱。存 A 的谱，同时记一个 A 与 B 的最大相对偏差作为标量——两张本该统计一致，偏差过大说明这一对里有一张出了事。

### 5.4 产出

两个文件。标量表：

```
#Format: JPTC-DARK/1
#AdcStep: 1
#ClipSigma: 3.5
#ClipCorrection: 0.9969
… 模式字段 …
ISO,ShutterSec,N,FileA,FileB,
R_BLa,G1_BLa,G2_BLa,B_BLa,
R_BLb,G1_BLb,G2_BLb,B_BLb,
R_StdA,G1_StdA,G2_StdA,B_StdA,
R_StdB,G1_StdB,G2_StdB,B_StdB,
R_StdDiff,G1_StdDiff,G2_StdDiff,B_StdDiff,
R_Clipped,G1_Clipped,G2_Clipped,B_Clipped
```

`StdDiff` 是 `A−B` 的标准差**原值，不除 √2，不做 Sheppard 修正**。剪切已经做了（因为它需要原始像素，分析端做不到），剪切参数写在头里，修正是可复算的。

#### 谱文件：纯文本，不需要二进制

先算体积。以 G9 II 为例，5776×4344 的 mosaic 拆完是每通道 2888×2172，于是横谱 1445 个 bin、纵谱 1087 个 bin。每 ISO 是 `4 × (1445 + 1087) × 2 = 20256` 个数，二十档 ISO 合计约 40 万个数——float32 才 1.6 MB。**小到根本不值得设计一个二进制格式。**用 CSV，人能读、能 diff、任何东西都能直接打开。

横纵 bin 数不同，所以分两个文件：

```
…_spectrum-h.csv     行 = 频率 bin（0 … 1445），列 = 每个 (ISO, 通道, 来源)
…_spectrum-v.csv     行 = 频率 bin（0 … 1087），同上
```

```
#Format: JPTC-SPECTRUM/1
#Axis: horizontal
#Window: hann
#Normalisation: 1/sum(w^2)
#FreqUnit: cycles-per-channel-pixel      (bin k -> k/N; x2 for sensor pixels)
#N: 2888
#DiffPowerFactor: 2
#RowsAveraged: 2172
… 模式字段 …
bin,freq,iso50_R_single,iso50_R_diff,iso50_G1_single,iso50_G1_diff,…
0,0.000000,…
1,0.000346,…
```

配套一个小表记每条谱的元信息：A/B 一致性偏差、参与平均的行数、被剪掉的像素比例。

## 6. 阶段 2：入口 2 —— ISO gain 阶梯

### 6.1 测量原理

固定场景、固定光圈，则每通道

    DN − BL = Φ · t / g

于是任意两档

    g₁ / g₂ = (t₁ / t₂) · (DN₂ − BL₂) / (DN₁ − BL₁)

**不要求「曝光正确」。**只要电平落在不钳位、不埋进底噪的区间即可。工具实测每张的电平，测光误差因此完全不进入结果——若依赖「曝光正确」，测光差 1/3 档就是 26% 的 gain 比误差。

暗电流在这里自动抵消：它也正比于 `t`，等效于 `Φ → Φ + D`，比值不变。这正是长曝光降噪必须关闭的原因——它只在部分帧上减暗电流，那才会破坏比例。

### 6.2 两种阶梯，都支持

**同快门配对（推荐）。**每个快门时间下拍相邻两档 ISO：

    快门 t_a:  ISO₁ → L₁,  ISO₂ → L₂   ⟹  g₁/g₂ = L₂/L₁
    快门 t_b:  ISO₂ → L₃,  ISO₃ → L₄   ⟹  g₂/g₃ = L₄/L₃
    链式相乘

`t` 从头到尾不出现。只要求快门在**同一对之内可重复**，不要求它准。这消掉了本方法最大的系统误差:从 RAW 读到的是**标称**快门时间，机械快门的实际值系统性偏离标称，而这个偏离读不出来。

**自动快门扫 ISO（快速）。**你原来的流程，一档 ISO 一张。快，但吃快门标称值的准确度。

两条路径都跑，把两条曲线画在一起。**它们分歧的地方就是快门标称值不准的地方**——这本身是有用的产出，不是缺陷。

### 6.3 拍摄流程（呈现给对方）

三脚架或把机器压在稳固处，对准均匀墙面。固定光圈——**优先手动光圈镜头**，电子光圈每次曝光重新收缩会带来重复性误差。光源须为直流或日光：市电 LED / 荧光灯在 1/500 s 下会造成大幅电平波动。

### 6.4 产出

```
#Format: JPTC-ISOGAIN/1
#Ladder: paired-shutter | auto-shutter
… 模式字段 …
ISO,ShutterSecNominal,Aperture,File,PairGroup,N,
R_Mean,G1_Mean,G2_Mean,B_Mean,
R_Std,G1_Std,G2_Std,B_Std,
R_ClipFrac,G1_ClipFrac,G2_ClipFrac,B_ClipFrac
```

**只记电平，不算 gain 比。**比值的算法（用哪条链、怎么加权）会演进，而电平不会。原始记录留在原始层。

## 7. 阶段 3：入口 1 —— PTC 平场对（本文档只作占位）

单 ISO，多快门，两两配对的平场。取中心 512×512 mosaic（= 每通道 256×256，65536 个样本），差分，k=3.5 剪切与修正，逐通道记 `StdA` / `StdB` / `StdDiff`。

产出即已定稿的 **JPTC/2** schema，直接进 ptc-compare。

## 8. 与 ptc-compare 共享什么

只有两样：**CSV schema** 与**拟合数学**。两边各存一份拷贝，用同一组黄金测试钉住数值一致——把它们做成 npm 包会让两个仓库的发布节奏绑死，收益不抵成本。

不共享 UI、不共享构建、不共享依赖。ptc-compare 是你自己的分析页，ptc-collect 是发出去的采集端，混在一起会把你的机型库随应用一起发出去。

## 9. 已定与未定

已定：

- **中心裁切 512×512 指 mosaic 像素**，即每通道 256×256 = 65536 个样本
- 入口 2 的墙面与入口 1 的平场装置有重叠，**不作特殊说明**，由使用者自行调节
- 分发从 GitHub Releases 走。注意这与 ptc-compare 的处置不同：**ptc-compare 保持纯本地、不上 GitHub**；只有 ptc-collect 需要到别人手上。发布时机由你决定，我不会自行推送。

- **只发 Windows。**不做 macOS 构建，不需要签名与公证。Windows 未签名会有 SmartScreen 警告，可绕过。
- 谱是 16 条一维谱，纯文本 CSV，不做二进制格式（见 §5.3）

未定：

- 是否需要一个「一键自检」模式：对方拍三张就能确认整套设置对不对，再去拍完整序列。我倾向于要——让一个不熟悉的人拍完六十张才发现长曝光降噪没关，那六十张全废，而且你还得远程隔空排查。
